## 1. The design in ten decisions

| #   | Decision                                                                                                                                                                                                                                                                               | Why                                                                                                                                                                          |
| --- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| D1  | An entry is a **logical entry** with a stable id. Every change writes a new **immutable version**; the old one stays.                                                                                                                                                                  | Ends delete-and-reinsert, the cause of #299, #311 and #313 and of the MCP id trap.                                                                                           |
| D2  | A version owns its **day segments** (the midnight split). Segments are stored, not computed by readers, and never outlive their version.                                                                                                                                               | Readers keep counting per day as today; a pair can no longer be half-edited or half-deleted.                                                                                 |
| D3  | There is **one write function** with **patch semantics**: a caller sends only what changes, everything else is copied from the current version.                                                                                                                                        | A caller that forgets a field can no longer reset it (#313 was exactly that).                                                                                                |
| D4  | While a timer runs, its version is **open** and may be amended in place; **stop seals it**. Sealed versions never change. Heartbeats live on the logical entry, not in versions.                                                                                                       | No version noise every few seconds; capture is complete at stop.                                                                                                             |
| D5  | The old table becomes a **read-only view named `entries`** that shows the current segments of live entries. Any leftover direct write against it fails loudly.                                                                                                                         | Most of the roughly fifty read queries keep working on day one; no writer can bypass D3 unnoticed (today seven places outside the mutation module write the table directly). |
| D6  | **Money is computed in one place:** a view adds `billed_minutes`, `rate_cent` and `fee_cent` per segment, from the frozen run if the segment is billed, otherwise from rate history and billing profile. PDF, CSV, Auswertung, budget, dashboard, webhooks and MCP read those columns. | One rounding rule, as #285 taught; a fourth minute rule cannot appear in a reader.                                                                                           |
| D7  | **Rates get `valid_from`** per client and per project; the rate of a segment is the one valid on its local date.                                                                                                                                                                       | Raising a rate no longer rewrites old months.                                                                                                                                |
| D8  | A **billing profile** per client with field-wise project override holds interval, minimum unit, clock-time alignment, column set, language, fee column and default grouping. Today's global setting becomes the default profile.                                                       | Each client dictates its own format (ZEP allows only :00/:15/:30/:45).                                                                                                       |
| D9  | A **billing run** freezes the **complete rule** (profile snapshot, rates, sender and recipient blocks), references the **exact versions** it billed, and archives the PDF with its hash. Billed entries can be changed only with a reason; a run can be released as a unit.            | The document at the client stays reproducible whatever changes later.                                                                                                        |
| D10 | A billing run is never silently re-issued: re-export returns the archived file; billing a correction means releasing the run (with reason) and creating a **new run with a new number** that names the one it replaces.                                                                | The owner's Q2 rule: no new content under an old number.                                                                                                                     |

## 2. Acceptance criteria (what the owner checks)

The design is accepted when the owner can answer yes to each of these from the document, and the build is accepted when each has a passing test or report:

1. **Schema:** for any amount on a PDF it is possible to name the entry version, the rule (interval, minimum unit, alignment) and the rate that produced it (sections 4, 8).
2. **Migration:** on a copy of the owner's database, every month's billed minutes, revenue, worked time and budget figures are identical before and after the migration, except the cases the migration report lists by entry with a reason (section 10).
3. **Write path:** the scenarios of #299 (calendar anchor), #311 (other half of a pair) and #313 (idle prompt fields) are impossible by construction, and each has a test through the real caller (sections 5, 11).
4. **MCP:** an id returned by `create_manual_entry` stays valid after any number of edits; `update_entry_fields` returns the same id with a higher version (section 9).
5. **Run lifecycle:** create a run, change the client's profile and rate and one billed entry afterwards: the run's frozen numbers and the archived PDF's hash stay the same, and the changed entry shows up as "changed since billed" (sections 8, 11).
6. **Open questions:** each item in section 3 has an owner answer (done 2026-10-23).

## 4. Data model

All times are stored as today: UTC ISO with milliseconds and `Z`. "Local date" means the date in the zone the process runs in, as the readers use today.

### 4.1 `entry`: the logical entry

| Column                                  | Notes                                                                                                                                                                                     |
| --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `id INTEGER PRIMARY KEY AUTOINCREMENT`  | Stable, never reused. Migrated entries keep the id of their first 1.x row; new entries start above the highest 1.x row id (section 10).                                                   |
| `created_at TEXT NOT NULL`              | First capture. Written once, never updated.                                                                                                                                               |
| `created_source TEXT NOT NULL`          | `app`, `timer`, `import`, `mcp`, `controller`, `migration`.                                                                                                                               |
| `current_version_id INTEGER NOT NULL`   | Pointer to the current version. The only column a write updates besides the two below.                                                                                                    |
| `is_deleted INTEGER NOT NULL DEFAULT 0` | Mirror of the current version's `deleted`, for indexes.                                                                                                                                   |
| `heartbeat_at TEXT`                     | Only meaningful while the current version is open. Not versioned.                                                                                                                         |
| `graph_event_id TEXT`                   | Calendar import anchor. Belongs to the entry, so no edit can drop it (#299). Unique where `is_deleted = 0`; an undelete whose anchor a later import has reused is refused with a message. |

`entry_legacy_id` maps every 1.x row id to its entry, so ids stored by MCP clients before 2.0 keep resolving (section 9).

### 4.2 `entry_version`: immutable content

| Column                                                                                                                | Notes                                                                                             |
| --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------- |
| `id INTEGER PRIMARY KEY`                                                                                              |                                                                                                   |
| `entry_id`, `version_no`                                                                                              | `version_no` counts from 1 per entry; unique together.                                            |
| `state TEXT NOT NULL`                                                                                                 | `open` (timer running) or `sealed`.                                                               |
| `deleted INTEGER NOT NULL DEFAULT 0`                                                                                  | A delete is a version with `deleted = 1` that carries the previous content.                       |
| `client_id`, `project_id`, `description`, `started_at`, `stopped_at`, `tags`, `reference`, `billable`, `private_note` | As today. `stopped_at` is NULL only while `open`.                                                 |
| `written_at TEXT NOT NULL`                                                                                            | When this version was written.                                                                    |
| `source TEXT NOT NULL`                                                                                                | `app`, `quicknote`, `idle`, `import`, `mcp`, `controller`, `tag-rename`, `migration`, `recovery`. |
| `reason TEXT`                                                                                                         | Required when the entry is billed (D9, OQ3); otherwise optional.                                  |

Only an `open` version may be updated in place (amending a running timer, sealing it). Everything else is append-only. A trigger rejects `UPDATE` on sealed versions, so the rule does not depend on discipline.

### 4.3 `entry_segment`: the day split

| Column                     | Notes                                                                        |
| -------------------------- | ---------------------------------------------------------------------------- |
| `version_id`, `seq`        | Primary key. `seq` 0, 1, 2 … in day order (a 48-hour timer has three).       |
| `segment_date`             | Local date of the segment's start, stored at write time. Unique per version. |
| `started_at`, `stopped_at` | Segment bounds; `stopped_at` NULL for the open version's single segment.     |

Written together with the version, from `splitAtMidnight` as today. Rewritten only while the version is open (at seal). A patch that leaves `started_at` and `stopped_at` unchanged copies the current version's segments as they are, so a 1.x row that crosses midnight unsplit keeps its shape and its billing.

`seq` only orders the segments of one version; an edit that adds or removes a day renumbers them. Anything that has to recognise "the same day of this entry" across versions (the billing lock in 4.6) uses `segment_date`, which an edit cannot shift: the 1 November part of an entry stays the 1 November part when the entry is extended back into 31 October.

### 4.4 Rates: `rate`

| Column                      | Notes                                                                                                            |
| --------------------------- | ---------------------------------------------------------------------------------------------------------------- |
| `client_id` or `project_id` | Exactly one set.                                                                                                 |
| `rate_cent INTEGER`         | For a project, NULL means "inherit the client rate from this date". 0 stays a deliberate 0 (goodwill), as today. |
| `valid_from TEXT NOT NULL`  | Local date.                                                                                                      |

The effective rate of a segment is the project's rate valid on the segment's local start date if one exists and is not NULL, else the client's rate valid on that date, else 0. Migration writes today's `rate_cent` values with `valid_from = '0001-01-01'`.

### 4.5 Billing profile: `billing_profile`

One row per client (and optionally per project, per field overriding the client; NULL means inherit), plus one default row (both ids NULL) that replaces today's settings.

| Field          | Values                                                                                                                        | Today                               |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------- | ----------------------------------- |
| `interval_min` | 0 (off), 1 to 60                                                                                                              | global `pdf_round_minutes`          |
| `min_unit_min` | 0 or more                                                                                                                     | does not exist (0)                  |
| `alignment`    | `none` (stored clock times plus a rounding footnote), `grid` (start snapped to the interval, end = start plus billed minutes) | `grid` whenever the interval is set |
| `columns`      | `times` (date, from, to, activity, duration, fee) or `no_times` (date, activity, duration, fee)                               | `times`                             |
| `language`     | `de`, `en`                                                                                                                    | `de`                                |
| `fee_column`   | `auto`, `on`, `off`                                                                                                           | `auto` (shown when a rate exists)   |
| `group_by`     | `none`, `tag`, `project`, `reference`                                                                                         | remembered per export               |

Alignment changes only what the PDF and CSV print. Stored times never change.

### 4.6 Billing runs: `billing_run`, `billing_run_item`, `billing_run_document`

`billing_run`: `id`, `number` (unique), `client_id`, `project_id` (nullable), `period_from`, `period_to`, `created_at`, `status` (`active` or `released`), `released_at`, `release_reason`, `replaces_run_id`, `invoice_ref` (the "invoice no." field, editable at any time), `rule_snapshot` (JSON: the resolved profile of the client and one resolved profile per project of the run that overrides a field, keyed by project id, so a client-wide run with different project rules can prove the rule of every item; sender block, recipient block, the logo image itself as a data URL, app version, run date; `saveLogo` and `removeLogo` delete the previous image file, so a hash alone could not reproduce the HTML), `html_sha256`, `pdf_sha256`.

`billing_run_item`: `run_id`, `entry_id`, `version_id` (the version billed), `seq` and `segment_date` (one row per billed segment), `billed_minutes`, `rate_cent`, `fee_cent`, `active` (mirrors the run's status). The rule that produced an item is the snapshot profile of the project of its `version_id` (the client's profile when that project overrides nothing). A partial unique index on `(entry_id, segment_date)` where `active = 1` is the lock: a day of an entry is in at most one active run, whatever later edits do to `seq`. A day that an edit adds to a billed entry is unbilled and can go into its month's run; a billed day that an edit removes keeps its item and shows as "changed since billed". A run takes the segments whose `segment_date` lies in its period, as exports select rows today, so the halves of an entry over a month boundary (31 October to 1 November) go into the October and the November run. An entry counts as billed when any of its segments is.

`billing_run_document`: `run_id`, `kind` (`pdf`, later `csv`), `bytes` (BLOB), `sha256`. The archived file lives **in the database**, so the existing backup and restore (which copy the SQLite file) carry it; a file in the data folder is only an export of it.

Items point at the **version**, not only the entry: a later edit creates a new version and leaves the run's input untouched.

## 5. The write path

`src/main/entryMutations.ts` gets one entry point, sketched as

```ts
writeEntry(db, op, ctx: { source, reason?, now }): IpcResult<EntryView>
```

with `op` one of `create`, `start` (creates an open version, seals whatever runs at the same instant, as `switchTimer` does today), `seal` (stop, idle stop, crash recovery), `amend` (patch of an open version), `patch` (patch of a sealed entry: new version), `delete`, `undelete`. Each runs in one transaction:

1. Load the entry and its current version. A patch is merged onto the current version; fields not in the patch are copied, never defaulted (D3).
2. Validate the merged result once, with the rules of the operation, as today:
   - `create`, and `patch` when it changes `started_at` or `stopped_at`: the manual-entry rules (valid range, start not in the future, 24 h cap, field limits, project belongs to client, overlap against current segments of other live entries of the same client).
   - `patch` that leaves the times alone (description, tags, project, a tag rename): the field limits and the project rule only; if the patch changes `client_id`, also the overlap check against the new client's entries. The range itself stays as it is, even if a sealed timer ran over 24 hours or a recovered entry has zero length.
   - `start`: today's `switchTimer` rules (client and project valid, start not before the running entry's start, not more than a minute ahead).
   - `seal`: only `stopped_at >= started_at`. No 24 h cap and no overlap check, as `stopEntry` today; zero length is allowed, because crash recovery without a heartbeat seals at the start (`recoverZombieEntries` does that today). A zero-length or same-day range yields one segment.
   - `amend`: the field limits and the project rule.
3. Lock check: if any segment of the entry has an active `billing_run_item` and the change is not exempt (OQ3), a missing `reason` fails with a "billed" error.
4. Write the new version (or amend the open one), its segments, and move `current_version_id`.
5. Return the entry view (id, version, segments, billed state).

How today's operations map onto it:

| Today                                                        | 2.0                                                                                                                       |
| ------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------- |
| `createManualEntry`, calendar import                         | `create` (import passes `graph_event_id` to the entry)                                                                    |
| `updateManualEntry` (delete and reinsert)                    | `patch`. The id stays; the anchor is on the entry; the other half of a pair is part of the same version (#299, #311 gone) |
| `switchTimer`, `startTimer`                                  | `start`                                                                                                                   |
| `stopEntry`, `stopRunningTimer`                              | `seal` (splits at midnight per OQ2)                                                                                       |
| idle "stop at idle"                                          | `seal` with `stopped_at` = idle start. No fields are sent, so none can be lost (#313)                                     |
| idle "mark as pause"                                         | `seal` at idle start, then `create` of a non-billable pause entry                                                         |
| quick note                                                   | `patch` with the description (OQ5)                                                                                        |
| `entries:delete` / `entries:undelete` (IPC, direct `UPDATE`) | `delete` / `undelete` of the whole entry                                                                                  |
| `entries:heartbeat` (direct `UPDATE`)                        | updates `entry.heartbeat_at`, no version                                                                                  |
| `recoverZombieEntries` (direct `UPDATE`, db.ts)              | `seal` with source `recovery`                                                                                             |
| tag rename and merge (direct `UPDATE ... REPLACE`)           | `patch` per live entry with source `tag-rename`; billed entries get the reason "Tag renamed" automatically                |
| graph import freeing the anchor on deleted rows              | unnecessary: the unique index ignores deleted entries                                                                     |

_Amended 2026-10-27 (owner decision, confirmed builder decisions of P2):_ a `patch` or `amend` that changes nothing once merged (after trimming) writes no version and returns the entry as it is. `delete` of a running entry seals it first, at `now` (the open version gets `written_at = now`; at the entry's start if `now` lies before it), then appends the deleted version, so no version in the trash is open. An edit that arrives without `segment_seq` (MCP, which fills unchanged times from the entry's range) applies its times to the whole entry. The description is trimmed on every write.

After this, nothing outside `writeEntry` writes the three entry tables. The view named `entries` cannot be written at all, so a forgotten direct writer fails in tests instead of bypassing the history.

## 7. Money: one rule

**The rule** stays in one function in `src/shared/currency.ts`, extended by the minimum unit:

```
raw = whole minutes of the segment, rounded up (0 stays 0)
billed = raw == 0 ? 0 : ceil(max(raw, min_unit) / interval) * interval   (interval 0: max(raw, min_unit))
fee = round(rate * billed / 60)
```

Its SQL twin takes column expressions instead of constants, because interval and minimum unit now differ per row. `revenueSql.test.ts` keeps proving the two agree.

**Where it is applied:** a view `billing_lines` (one row per current segment of a live entry) carries:

- `billed_minutes`, `rate_cent`, `fee_cent`: from the run's item if the segment's version is billed in an active run, else computed with the rule from the resolved profile and the rate valid on the segment's local date;
- `billed_run_id`, `billed_version_id`: the active run item for this entry and `segment_date`, if any.

**"Changed since billed"** is defined from the run's side, not from `billing_lines`, because a deleted entry or a billed day that an edit removed has no current segment at all. A view `billing_changes` takes every active `billing_run_item` and joins the entry's current version and its segment with the same `segment_date`. An item is changed when the entry is deleted, when the current version has no segment on that date, or when that segment belongs to a different version than the one billed.

The running timer's open segment carries no money columns (`rate_cent`, `fee_cent` are NULL) until it is sealed, as today, where readers of money skip `stopped_at IS NULL`. Its `billed_minutes` is not NULL: it is provisional, computed with the same rule from the segment start to now, because today's `readRoundedTotals` counts a running entry up to now and Heute and the Stream Deck must keep showing it. The provisional value is never stored, never enters a run, and becomes final when the segment is sealed.

Every reader in section 6 that shows money or rounded time reads these columns and nothing else. The constant `pdf_round_minutes` and its seven readers disappear; the default profile replaces them.

**Rate history, freezing and the profile together:** an unbilled segment follows the rate valid on its date and the current profile; a billed segment shows exactly what its run froze, even after a rate rise, a profile change or a correction of the entry (the correction shows as a new current version with its own computed numbers, and as "changed since billed").

## 8. Billing run lifecycle

1. **Create** (Export tab, option "mark as billed"): the export resolves the profile, computes the lines, writes `billing_run` with the full `rule_snapshot` and one item per segment, renders the HTML, stores `html_sha256`, prints the PDF, stores its bytes in `billing_run_document` and its `pdf_sha256`. Segments already in an active run are excluded with a notice. An export without the option stays possible and leaves no trace, as today.
2. **Billed state:** entries with an active item show a "billed" chip and a lock symbol (UI per the Messinstrument vocabulary, details in the UI PR).
3. **Change with reason:** a patch or delete of a billed entry needs a reason (OQ3); it writes a new version; the item keeps pointing at the billed version.
4. **Re-export:** opening a run returns the archived PDF. Re-rendering from the frozen inputs must give the same `html_sha256` (a check, not the delivery); for that, `rule_snapshot` holds every input of the HTML, the run's date included, and nothing in the HTML reads the clock. The PDF hash itself is not re-derived, because Chromium writes a creation date into every PDF.
5. **Release** ("Lauf lösen"): with a reason, as a unit: the run becomes `released`, its items inactive, its segments unbilled. The archive stays.
6. **Re-bill:** a new run with a new number, `replaces_run_id` pointing at the released one (OQ4).
7. **Invoice no.:** `invoice_ref` can be filled in at any time without a reason; it is metadata about the run, not part of the content.

**Invariant (and its test):** after a run is created, changing the client's profile, its rate, the sender data and one billed entry leaves the run's items, its `html_sha256` (re-rendered from the frozen inputs) and the archived `pdf_sha256` unchanged; the changed entry appears in "changed since billed".

## 9. MCP, webhooks and other contracts

This is a major release; the changes are listed under "Breaking for MCP clients and integrations" in the CHANGELOG.

- **Ids:** every tool addresses the logical entry id. Ids of migrated second halves resolve to their entry through a lookup table for the whole 2.x line, so ids a client stored in 1.x keep working. _Amended 2026-10-27 (owner decision):_ the id of a second half resolves to the entry and names that half, so an edit through it behaves as in 1.x. The half is found by the start of the 1.x row in `entries_v1`, matched to the segment of the entry's first version, and its `segment_date` names it from then on (fallback when the 1.x row is missing: the rank of the id among the entry's legacy ids). If an edit has shortened the entry so that the half is gone, changes to fields go through and changes to times are refused.
- `update_entry_fields`: returns the entry with the **same id** and its new `version`. New optional `expected_version`: if the entry moved on since the client read it, the write is refused instead of overwriting. New `reason`, required for billed entries; the preview and the confirmation dialog say when an entry is billed.
- `create_manual_entry`: returns the new entry's id and `version` 1.
- `list_entries`: one item per entry (OQ7) with `version`, `source`, `created_at`, `billed` (run numbers or null) and `segments` when there is more than one; money fields from `billing_lines`. _Amended 2026-10-27 (owner decision, 2026-10-26):_ an entry appears when any of its segments starts in the window. `count` counts entries; `total_seconds` sums only the segments inside the window, so a month's total agrees with the calendar and the PDF; `duration_seconds` on an item is the entry's whole duration.
- New read tool `get_entry_history`: the versions of one entry with source, time and reason.
- `get_analytics`, `list_projects`, `get_dashboard`: same shapes, numbers from `billing_lines`.
- **Webhooks:** `entry.id` is the stable id, plus `version`. `entry.deleted` (Q31) fits naturally and is planned with the integration contract, not here.
- **Audit log:** `mcpAudit` stays as a transport log; the history now lives in the versions themselves.
- **Known limitation** _(amended 2026-10-27, owner decision, deliberate)_: an explicit `started_at` through the entry id that equals the start of a later segment is applied to the whole entry, i.e. as a shortening of its start. There is no guard against it.

## 10. Migration from 1.x

One numbered migration, inside the runner's existing backup-and-restore. It runs in one transaction and checks its own result before committing.

1. **Group rows:** rows sharing a `link_id` form one entry; every other row is its own entry. The entry id is the smallest row id of the group, so single rows and first halves keep their ids. `entry_legacy_id` maps every 1.x row id to its entry. The migration seeds the `AUTOINCREMENT` counter of `entry` with the highest 1.x row id, so a new entry can never get the id of a migrated second half (legacy rows 10 and 11 become entry 10; the next new entry is 12, not 11).
2. **Content:** version 1 per entry with the row's fields, `source = migration`, `written_at = created_at`. Segments are the 1.x rows exactly as stored, including timer rows that cross midnight unsplit (OQ2), so per-segment billing of old months does not change.
3. **Deleted rows:** an entry whose rows are all deleted gets a second version with `deleted = 1` and `written_at = deleted_at`. A pair with one half deleted is split into two entries (OQ8).
4. **Running entry:** an open version; `heartbeat_at` goes to the entry.
5. **`created_at`:** the earliest `created_at` of the group. For entries edited in 1.x this is the time of the last edit (#299); the migration cannot recover the original and does not pretend to.
6. **`graph_event_id`:** moves to the entry (it sits on one half today).
7. **Rates and profile:** today's rates become `rate` rows from `0001-01-01`; `pdf_round_minutes` becomes the default profile with `alignment = grid` when it is set, so PDFs look as before until the owner changes a client's profile.
8. **Keep the old table** renamed to `entries_v1`, read-only, for the 2.x line (comparison and support).
9. **Self-check before commit:** per client and month, the old formulas over `entries_v1` and the new views must agree on worked seconds, billed minutes and revenue (rounded and unrounded). With the choices above (segments kept as stored, half-deleted pairs kept apart, the default profile equal to today's setting) no difference is expected, so any difference aborts the migration. A report is written to the log folder: counts per shape (single, pair, half-deleted pair, unsplit timer row over midnight, zero-length recovered entry, running entry, imported entry) and every exception by id.

`rounded_min` is dropped from the model; it has had no reader since #285.

## 11. Test strategy

1. **Rule with independent expected values:** a table of hand-computed cases for the one rounding rule, not derived from the code: interval edges (exactly 15:00, 15:01, 14:59.999), minimum unit larger and smaller than the interval, interval off, zero length, a project override of only the interval, rate change on the segment date, frozen rule after a profile change. The JS rule and its SQL twin are both checked against this table.
2. **Agreement across readers:** for one seeded data set, PDF, CSV, Auswertung, budget, rounded totals, webhooks and MCP `get_analytics` give the same billed minutes and revenue per client and month, and those totals equal the hand-computed expected values from (1). Four sums agreeing is not enough on its own, because they can all be wrong together.
3. **Write path properties:** for every operation and a generated set of entries (single, pair, billed, imported, running), every field not in the patch is identical in the new version; ids never change; `created_at` and `graph_event_id` never change.
4. **Bug-class regressions through the real callers:** #299 (edit an imported entry; the preview no longer offers the meeting), #311 (MCP edit of one half keeps both segments and the total duration), #313 (idle stop and mark-pause keep project, billable flag, tags, reference and note), the quick note, and the cases of #335: an edit of a deleted entry is refused, including over MCP when the entry is deleted between preview and confirmation; an undelete that would overlap is refused; an edit of the second half returns the entry with both segments; a description-only save from the edit form keeps the seconds of the end.
5. **No bypass:** a test that every write to the entry tables in `src/` goes through `writeEntry` (writing to the `entries` view throws; a grep guard over the source for `INSERT INTO entry`, `UPDATE entry`).
6. **Run lifecycle:** the invariant in section 8; lock with and without reason; release; re-bill with `replaces_run_id`; a day of an entry in at most one active run; a midnight pair billed as two items in one run; an entry over a month boundary billed half in each month's run; a billed 1 November entry extended back into 31 October keeps its November day locked and offers only the new October day for billing; a logo replaced or removed after the run leaves the re-rendered `html_sha256` unchanged; restoring a backup brings back the archived PDF with an unchanged hash; a tag rename succeeds on a zero-length recovered entry and on a timer over 24 hours.
7. **Per-operation validation:** sealing a timer that ran more than 24 hours, and a zero-length crash recovery, both succeed; a switch never fails because of the seal; a `create` or `patch` over 24 hours is refused as today; moving an entry to another client is refused when that client has an overlapping entry; a description edit on a migrated row that crosses midnight unsplit keeps one segment and its billed minutes.
8. **Ids and iCal:** after migrating a database whose highest row ids are a pair, the next new entry gets a fresh id and the old second-half id still resolves to its entry; feed and static iCal export give the segments of a pair distinct UIDs that stay the same when an edit adds a day in front; `billing_changes` lists a deleted billed entry and a billed day that an edit removed.
9. **Migration on realistic data:** a seeded generator produces every shape in section 10 (including the 1.x defects: unsplit timer rows, half-deleted pairs, zero-length recovered rows, edited entries with a late `created_at`, imported entries with the anchor on either half) and the migration's self-check must pass on it in CI. In addition, one run against a **copy** of the owner's latest backup (never the live database, never committed) between P1 and P2 (L7), and again before the 2.0 tag, each time with the report reviewed by the owner. This is acceptance criterion 2.
10. **Performance:** a 50 000-entry fixture; the month view and the Auswertung stay within today's times.
11. **Running timer in rounded totals:** with only a running entry, Heute and the Stream Deck rounded sums are not zero and equal the rule applied from the segment start to now; after sealing, the value equals the stored `billed_minutes`.

## 12. What would make this fail

- **A reader keeps its own arithmetic.** If one of the readers in section 6 still computes money itself, the fourth minute rule of #285 comes back. Watch: test 11.2 and a grep guard for `billedMinutes` outside `currency.ts` and the view.
- **The view hides a semantic change.** A reader that relied on two rows having two ids (keys, counts) silently counts differently. Watch: the reader-by-reader parity check in the migration self-check, and the renderer key change in P3 (section 13).
- **The migration self-check is too strict for real data.** Real databases hold shapes the generator does not know; the migration then refuses to run on the owner's machine. Watch: the run against the backup copy before the tag, and a report that names every exception instead of a single failure.
- **Capacity.** The workshop note names it: the foundation is L plus several M for a solo maintainer. Watch: whether this document is accepted within two weeks of the 1.23.0 tag.
- **A change of the system time zone.** `segment_date` is written once, in the zone the process runs in; the readers that still cut months from instants (`entryRanges.monthEntries`) use the zone of the moment they run. After a zone change a run and the calendar can disagree about which month an entry near midnight belongs to (`2026-10-31T23:30Z` is 1 November in Berlin and 31 October in UTC). This is a known limit, as it is in 1.x (Falle 13 of the owner map), not a defect this design introduces; 2.0 makes it visible because the date is stored. Watch: a test in P4 that sets the process zone after writing and compares the month of a run with the month of the calendar for an entry near midnight; if they differ, the readers move onto `segment_date`.
- **The render zone is not frozen.** `rule_snapshot` holds the inputs of the HTML, but the formatters in `pdf.ts` (`formatDate`, `formatTime`) use the zone the process runs in, and so does the grid alignment. After a change of the system zone and a restart, a re-render of the same run gives a different `html_sha256`. The archived PDF and its `pdf_sha256` are unaffected, so the delivery stays intact; only the re-render check of section 8 step 4 holds under an unchanged zone. Known limit, like the zone row above. Watch: a P5 test that re-renders a run under a changed zone and expects the documented difference; if the owner ever needs the check across zones, the zone goes into `rule_snapshot` then.
